# CORE-2363

## Requirement

As a CORE Engineer, I need to determine if there is a low-lift interim solution that can
be made available to internal teams and customers to improve semantic model usability,
so we can lessen the number of support requests and unblock customers from being able to
realize the full value of the models themselves.

  would make it confusing / impact trust for customers, so that method was abandoned.
- MCP-specific AI for semantic models found what was missing and gave suggestions for
  how to fill in the gaps. May be useful for getting started.
- Augie understands from a technical perspective really well. Not so good at providing
  context around what is the data, what does it mean.
- Likely good at mapping data points from source DB to model if given context from the
  transformation layer.
- May be worth looking into Ontology.
- Created a notebook to run against the transformations to surface metadata and compile
  things like facts, measures, descriptions and build out a file that can be moved to
  Confluence. AI mostly removed from this process.
  - Fact tables w/ related dimensions.
  - Dimension tables w/ related facts, for slicing / dicing.
  - Uses relationship data to identify direct relationships. Does not infer indirect
    relationships.

## Acceptance Criteria

- How/can we develop a low-lift solution to create documentation to help users
  understand how to use our semantic models?
- What dimensions, facts, measures, etc. are available?
- How data points are/can be related to each other?
- How "user-friendly" naming conventions map back to TransactionalDB tables/columns?
- What is the lift to do this for each baseline semantic model?
- Is this a one-time initial effort with manual updates, or is it possible to automate
  in the future?
- If it can be automated, what would the lift/cost be?

## Ticket Status

`semdoc` (this repository) is a working answer to the first acceptance-criteria
question, built and verified against four real baseline models in this tenant (HMIS
DirectLake, CaseWorthy Enterprise, Coordinate Semantic Model, ServTracker Semantic
Model). It splits cleanly into two halves that are at very different levels of
readiness relative to this ticket: the **factual half is done and effectively free to
re-run**; the **narrative half is proven but not yet automated**; and **getting it in
front of customers is not yet solved at all**. Detail against each criterion below.

### How/can we develop a low-lift solution to create documentation?

**Addressed, with a caveat on "low-lift."** The tool exists and produces two audience
variants (a technical reference and a business-facing report-building guide) from one
extraction, for any Fabric semantic model it's pointed at — not a one-off for a single
model. It also directly answers the trust concern raised in the Notes above (*"AI
regenerated the documentation... changed things that would make it... impact trust"*):
every extracted fact (tables, columns, DAX, relationships, RLS, warehouse lineage) is
read verbatim from the model and never touched by an LLM; anything AI-authored (plain-
English descriptions, a glossary, "what you can answer," gotchas) is generated
separately, checked against the model before being shown, and visibly labeled
`generated & verified` vs. `generated — unverified` right next to the content itself —
never silently presented as settled fact. This is the direct fix for the exact failure
mode that caused the earlier AI-regeneration approach to be abandoned.

The caveat: the **factual half is low-lift already** (a few CLI commands, minutes,
zero manual editing — see the lift breakdown below). The **narrative half is not
low-lift yet** — see the automation question below.

### What dimensions, facts, measures, etc. are available?

**Addressed.** Every table, column, measure (with verbatim DAX), relationship, and RLS
role is extracted directly from the model definition. Tables are automatically
classified as fact / dimension / bridge / calculation group / disconnected from the
relationship graph itself (not guessed), and the guide's sidebar groups tables by that
classification — literally *"fact tables"* and *"dimension tables"* as their own
groups, matching the notebook's existing fact/dimension split described in the Notes.

### How data points are/can be related to each other?

**Addressed, and one step further than the notebook this replaces.** The Notes
describe the prior notebook approach as using relationship data for **direct**
relationships only, with indirect relationships explicitly out of scope. `semdoc`
covers direct relationships the same way (a full model relationship diagram, plus a
lineage diagram back to the warehouse) — and additionally surfaces one specific,
genuinely useful *indirect* relationship: which fact tables relate to each other
*through* a dimension they both share (e.g., two fact tables that both connect to
`Client`), shown as both a diagram and a plain table. This was checked against real
data before being built: a naive "any shared dimension counts" version is a
near-complete hairball (on one model, every possible pair of fact tables shared at
least one dimension), so only dimensions genuinely shared by 2+ facts are shown — the
result stays small and readable rather than technically-complete-but-useless.

### How do "user-friendly" naming conventions map back to TransactionalDB tables/columns?

**Addressed.** Every model table and column is mapped back to its warehouse
table/column (schema-qualified) via a dedicated lineage pass over the SQL analytics
endpoint, shown both as a diagram ("Where the data comes from") and inline next to each
column in the technical reference. This is deterministic (read from the model and
warehouse metadata, not inferred by an LLM) — directly answering the mapping question
without the risk the Notes raise about an AI guessing at meaning it doesn't have
grounding for.

### What is the lift to do this for each baseline semantic model?

**Answerable now, with real numbers from four runs, not an estimate.**

The **factual pass** — extract, relationships, warehouse lineage, best-practice
findings (21 of the community Tabular Editor rule set's 30 rules), column
cardinality/sample values, existing-report usage — is a handful of CLI commands, each
a few minutes, entirely automated, no manual editing at any point. Observed scale
across the four real models run so far: 28–58 tables, 28–199 measures, 38–100
relationships, 129–807 profiled columns per model. All four finished with zero
extraction failures.

The **narrative pass** (plain-English table/measure descriptions, a glossary,
"what you can answer," gotchas) is where the real lift currently sits, because nothing
automatically drafts it — see the next question. For the three models where this repo
authored it this session: 51–54 tables and 27–62 measures needed a description each on
the two larger models (a third, already well-documented model needed exactly one). That
work also surfaced genuine, real problems in those models along the way — a measure
whose name and its logic disagree, a misspelled duplicate column, an inactive
relationship silently doing nothing — which is itself a point in favor of doing this
pass at all, automated or not.

**Not yet addressed at all: getting this in front of customers.** The ticket asks for
something "available to internal teams **and customers**." Today this is a local
Python CLI that needs Fabric credentials and a terminal — realistic for an internal
engineer, not for a customer, and not yet for most internal teams either. There is no
packaging, hosting, or distribution story yet (a follow-on idea already discussed:
publishing the generated guide/IR to a Lakehouse so it can be served instead of run
locally) — this is the largest open gap against the ticket's actual ask, independent of
how good the documentation itself is.

### Is this a one-time effort with manual updates, or can it be automated?

**Split answer, and this is the most important one for scoping next steps.** The
factual half is *already* fully automated — re-run the same commands after the model
changes and every fact, relationship, lineage mapping, and stat updates with no manual
work. The narrative half is *not* automated today: every description, glossary entry,
question, and gotcha in the four models built so far was authored by a person (working
through Claude Code) reading the real model and writing grounded content, then
mechanically validated — not generated by a single command.

### If the narrative half can be automated, what would the lift/cost be?

**Not yet built, but the shape of it is now well understood from doing it manually
four times.** It would be a new `semdoc enrich` command: call the Claude API once per
table/measure lacking a description (grounded in its real columns/DAX, the same
prompting approach already proven this session), run it through the identical
validation the manual path already uses (every identifier checked against the model
before anything is trusted), and attach the result the same way `narrative apply`
already does today. The validation and attachment machinery already exists and is
already exercised in production against real models — building `enrich` is specifically
about automating the *drafting* step, not inventing a new trust model for it. This is
the top item on this project's own "not yet built" list for exactly that reason.
